A small banking service

Money that arrives exactly once.

Tally moves money from one person's account to another and keeps a written record of every movement, so a payment can never quietly go missing and can never be paid twice.

Built by Abdul Samad Zeeshan as a study in getting the boring, critical parts right: Java behind the scenes, a React screen in front, and a great many tests.

You can send a payment yourself further down this page. Nothing to install, nothing to sign up for.

01

A payment has to land once, even when the line drops.

You tap send. Your phone loses signal before the answer comes back. Did the money go, or not? So you tap send again.

Now two requests exist for one payment, and only one of them may count. Get that wrong in one direction and somebody is charged twice. Get it wrong in the other and the rent never arrives. Tally is built around that single moment.

03

What you just watched.

  • Every payment was written down twice.

    One line for the money leaving, one line for the money arriving, exactly the same size. Add every line in the whole book together and you get nothing, which is why that green tag keeps saying 0.00. The panel calls this “double entry”. That is all it means.

  • The second send did not become a second payment.

    Every payment carries a label the sender makes up for it. The service remembers the label and the exact answer it gave the first time, so a repeat under that same label gets the same receipt handed straight back instead of moving money again. Run “Lose a response, retry safely” and watch Ben's balance move once, not twice.

  • Nothing is taken on trust. It gets recounted.

    Balances are stored, and they can also be worked out again by adding up an account's lines from the beginning. Tally keeps both and compares them on demand. If they ever disagreed by a single cent, the check would name the account rather than hide it.

04

The numbers, and how each one was measured.

Every figure here comes from the real Java service. None of it comes from the browser copy above.

210 tests 0 failures, 0 errors, 0 skipped.

How: the command ./mvnw test, run in this repository on 27 July 2026 on Java 25. That is the whole of what that one command reports, across 28 test files, and it is the only test count on this page. Tests that need a live database, and the deliberately broken version kept around to prove the bug, are run by different commands and are not counted here.

20,000 payments Pushed through by up to 32 workers at once.

How: a test harness shares 20,000 payments across 8 accounts and hands them to a pool of workers released together. The pool is two workers per processor core, never fewer than 8 and never more than 32, so at most 32 payments are ever in flight. Afterwards it checks the total is unchanged, that no balance ever went below zero, and that replaying the log of successful payments reproduces the final balances to the cent. Set in StressHarness.java, lines 39 and 42.

0.00 left over A recording of the real Java service answering.

How: the service was built at code version 1b44ebf, started, and driven with curl. Every reply was copied word for word into data/tally-run.json. In it: 3 accounts checked, the whole book adding to 0, no disagreements, a repeated request answered with the very same receipt plus a header marking it a repeat, and an overdraft refused with both numbers named. That file is real evidence, and it is the only recording on this page.

1 outside library Almost all of it is hand written.

How: the running service pulls in exactly one third party library, the Postgres driver, listed in pom.xml. The web server, the JSON reader and writer, the request routing and the database pool are all written by hand: 51 Java files, about 3,155 lines under src/main/java.

31 screen tests The screen has its own checks.

How: npm test in the web folder on 27 July 2026: 5 files, 31 tests, all passing, alongside a clean type check. They cover the money arithmetic, so that a value like 0.29 can never arrive on screen as 0.28999.

0 decimals used Money is counted in whole cents.

How: every amount is a whole number of cents from the database to the screen, so there is nothing to round and nothing to lose. No amount above a thousand billion cents is accepted, a limit set in Validation.java line 22, which keeps every total well inside what a browser can hold exactly.

The longer write up, guarantee by guarantee, including the concurrency bug that was written on purpose so the fix could be proved against the exact defect it closes, is in correctness.md.

05

What Tally does not do.

  • It never touches a real bank.Nothing here reaches a card network, a bank, or any payment rail. The account named world stands in for the outside world, and money only ever moves between accounts Tally holds itself.
  • One currency, and it is never named.Every amount is the same implied currency. A real system carries a currency on each account and refuses to mix two of them in one payment. That was left out on purpose, to keep the money model a single clear idea.
  • One server and one database, nothing spread out.The arguments about locking and about repeated requests are written so they would still hold with several servers running at once, but that is neither built nor tested, so claiming it would be guessing.
  • The password is fixed and in plain sight.The real service guards its write requests with a single password chosen when it starts. A real product would hand each person a short lived one from a login screen. The trade is written down rather than hidden, in decision record 15.
06

Where each piece actually lives.

  • The rule that makes it all add up Takes a payment and the accounts it touches, refuses it if the two sides do not cancel or if it would push somebody below zero, and hands back the new balances. It stores nothing. src/main/java/dev/tally/core/Ledger.java
  • Where the money and the written lines are kept Holds the accounts, remembers which payment labels have been used and what answer each one got, and writes both lines of a payment together so half a payment is never visible. src/main/java/dev/tally/store/InMemoryStore.java
  • The account named world The one account allowed to go below zero. Every opening balance is moved out of it, which is the reason the whole book adds to nothing from the very first account onward. src/main/java/dev/tally/core/WorldAccount.java
  • Two payments touching one account at the same time Each payment takes a hold on both of its accounts, always in the same fixed order, so two payments crossing in opposite directions can never end up waiting on each other forever. src/main/java/dev/tally/store/AccountLocks.java
  • The recount Adds every account's lines back up from the beginning, compares the result against the stored balance, and reports any disagreement as an ordinary answer rather than as a failure. src/main/java/dev/tally/api/ReconciliationHandler.java
  • The one place the screen talks to the service Six requests, and nothing else in the whole app reaches the network. That narrow gap is what made the browser copy on this page possible at all. web/src/api/client.ts
